# ai-data-center

AI-powered healthcare facility operations monitoring with automated anomaly detection.

# Healthcare Facility Operations Monitoring Dashboard

A lightweight, full-stack monitoring dashboard that simulates real-time hospital
unit operations metrics (bed occupancy, average wait time, patient backlog) for
a fictional healthcare facility, detects operational anomalies, and displays
them on a live web dashboard.

This project was an early exploration of the same core problem I later solved
at production scale with **PodSight**: ingest metrics, detect anomalies, and
surface them through a usable interface. It started as a generic server-metrics
demo and was reframed around healthcare facility operations, using synthetic
data only — this is not connected to any real hospital system or patient data.

It also doubles as a hands-on sandbox for practicing a few additional skills
(TypeScript, a React view, and a Node/Express API) next to the primary Python
stack, rather than a from-scratch rewrite.

## What it does

- Simulates live hospital-unit operations metrics (bed occupancy rate, average
  wait time, patient backlog) for multiple units
- Detects threshold-based anomalies and logs them:
  - Bed occupancy rate > 90% → "High Bed Occupancy"
  - Average wait time > 60 minutes → "Long Wait Time"
  - Patient backlog > 15 patients → "High Patient Backlog"
- Serves current metrics through two independent, functionally identical
  `/metrics` APIs — a primary Flask (Python) backend and a secondary
  Express (Node.js) backend — both reading the same JSON config file
- Displays metrics on two dashboard views:
  - The original vanilla dashboard, now written in TypeScript and compiled
    to JavaScript
  - A lightweight React dashboard loaded via CDN scripts, with no build step
- Includes a standalone Go version of the metrics loader (early exploration
  of a Go-based rewrite)

## Tech stack

- **Backend:** Python (Flask, primary), Node.js (Express, secondary — built
  for hands-on Node/Express familiarity alongside Flask), Go (early
  prototype loader, no API)
- **Frontend:** TypeScript (compiled to vanilla JS) + HTML/CSS, and a
  separate lightweight React view
- **Data:** JSON (seed/config data), CSV (alert logs)

## How it works

1. **`monitor.py`** loads unit metrics from `configs/sample_metrics.json`,
   randomly adjusts values each cycle to simulate real-time change, and
   checks each unit against fixed thresholds:
   - Bed occupancy rate > 90% → High Bed Occupancy alert
   - Average wait time > 60 minutes → Long Wait Time alert
   - Patient backlog > 15 → High Patient Backlog alert

   Alerts are logged to both a log file and `logs/monitoring_alerts.csv`.

2. **`app.py`** is a small Flask API that reads the current metrics file and
   exposes it at a `/metrics` GET endpoint, with CORS enabled for browser
   access. This is the primary backend.

3. **`server.js`** is a small Express API that exposes the exact same data
   at the same `/metrics` shape, reading from the same config file. It's an
   intentional second implementation of the same endpoint, written to build
   hands-on familiarity with Node/Express — it doesn't replace Flask, and
   the two are not meant to run as a coordinated pair.

4. **`script.ts`** (compiled to `script.js`) polls the `/metrics` endpoint
   every 3 seconds and renders each unit's bed occupancy, wait time, and
   patient backlog into the original dashboard (`index.html`).

5. **`dashboard.jsx`** is a small React functional component (using
   `useState`/`useEffect`) that does the same thing, rendered by
   `react-dashboard.html`. It loads React, ReactDOM, and Babel Standalone
   from CDN `<script>` tags directly in the HTML page — **there is no
   build toolchain here** (no Vite, no Create React App, no bundler). Babel
   Standalone transpiles the JSX in the browser at page-load time. This
   keeps the example dependency-free and easy to open directly, at the
   cost of the production build performance and tooling you'd get from a
   real React build pipeline.

6. **`scripts/go_version/`** contains an early Go implementation that loads
   and parses the same metrics JSON — a first step toward a Go-based
   rewrite of the monitoring logic. It only prints the parsed data; it has
   no API or dashboard integration.

## Running it locally

**Backend — Flask API (primary):**
```bash
cd web
pip install flask flask-cors
python app.py
```
This starts the API at `http://localhost:5000/metrics`.

**Backend — Express API (secondary, optional):**
```bash
cd web
npm install
node server.js
```
This starts a second, independent copy of the same API at
`http://localhost:5001/metrics`. It exists for Node/Express practice, not
as a replacement for the Flask backend — you don't need to run it for the
dashboards to work, since both dashboards point at the Flask API by default.

**Frontend — original dashboard (TypeScript, compiled):**
```bash
cd web
npm install        # installs the TypeScript dev dependency
npx tsc            # compiles script.ts -> script.js (or `npm run build`)
```
Then open `web/index.html` in a browser, or serve the `web/` directory with
any static file server. It fetches from `http://localhost:5000/metrics`, so
the Flask API must be running.

**Frontend — React dashboard (CDN, no build step):**
Just open `web/react-dashboard.html` in a browser (or serve it with a static
file server) with the Flask API running. No build step is required — the
page loads React, ReactDOM, and Babel Standalone from CDN links and
transpiles `dashboard.jsx` in-browser.

**Monitoring loop (anomaly simulation):**
```bash
cd scripts
python monitor.py
```
Runs 5 simulated monitoring cycles, updating metrics and logging any
threshold breaches.

**Go version (metrics loader only):**
```bash
go run scripts/go_version/monitor.go
```
Run this from the repository root so it can find `configs/sample_metrics.json`.

## Known issues / to fix

- [ ] No persistent database — metrics reset to the seed file on every load
      rather than tracking real history
- [ ] `monitor.py` and the APIs (`app.py`/`server.js`) don't share a live
      feedback loop — the dashboards read the static config file, not the
      values `monitor.py` is actively simulating
- [ ] Go version (`scripts/go_version/`) only loads and prints metrics — no
      API or dashboard integration yet
- [ ] The React dashboard's CDN/Babel Standalone setup is meant for
      learning and quick demos, not production — a real deployment would
      use a proper build toolchain (Vite, CRA, or similar) with a bundled,
      minified build instead of in-browser JSX transpilation
- [ ] API URLs in `script.ts`/`dashboard.jsx` are hardcoded to
      `http://localhost:5000`, not configurable via environment variable

## Possible next steps

- Connect `monitor.py`'s simulated updates to the same data source the
  APIs/dashboards read from, so the dashboards reflect live simulated
  changes rather than the static seed file
- Replace the flat JSON file with a real database (e.g. MongoDB, matching
  the approach used in PodSight) to support historical tracking and trend
  charts
- Deploy the API(s) and dashboards to AWS (e.g. Lambda + API Gateway for
  the backend, S3/CloudFront for the frontend) as a hands-on cloud
  deployment exercise
- Extend the anomaly model beyond fixed thresholds (e.g. rolling averages,
  rate-of-change detection) — similar to the counter vs. gauge metric
  handling used in PodSight
- Move the React dashboard to a real build toolchain (Vite) if it grows
  beyond a single demo component
